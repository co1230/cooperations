# 商城管理系统

一个零依赖、可直接在浏览器运行的电商后台原型，包含：

- 普通买家公开注册，以及普通买家、商家、管理员三种身份的登录
- 根据角色自动进入不同后台
- 买家登录后进入购物平台首页，可查看历史订单、体验模拟支付
- 用户、商品、订单、订单明细的 MySQL 8 数据库设计
- 购物车、收货地址、支付流水、售后工单和状态变更日志
- 订单状态与售后状态独立建模

## 运行

直接双击 `index.html`，或在本目录启动任意静态文件服务器：

```bash
python -m http.server 8080
```

然后访问 `http://localhost:8080`。

| 商家 | merchant@demo.com | 123456 |

公开注册固定创建普通买家账号。商家和管理员账号应由管理员后台创建；本原型可直接使用上方固定演示账号。

## 订单与模拟接口

登录买家账号后，点击右上角“我的订单”查看当前账号的历史订单。首页与订单列表均可执行模拟支付；支付成功后订单由“待付款”变为“待发货”，刷新或重新登录后状态仍保留。商家和管理员的订单表读取同一份数据。新注册买家没有历史订单，不会继承演示账号的订单。

- `mock-api.js` 提供异步的 `orderApi.listOrders()` 和 `orderApi.payOrder(orderId)`，从当前会话确定身份，不接受调用方传入买家 ID。
- 模拟数据存储在 localStorage 的 `ecom_order_db_v1` 中，包含订单、商品明细、售后工单、支付流水和状态日志。售后状态独立展示，付款不会覆盖售后状态。
- 字段、状态枚举与 `database/schema.sql` 对齐：`PENDING_PAYMENT` 显示“待付款”，`PAID` 显示“待发货”。未连接 MySQL，演示种子数据不是实际交易数据。
- 支付仅允许买家操作自己的待付款订单；重复支付已付款订单不会重复生成流水。旧版 `demo_order` 的已支付记录在首次初始化时迁移到固定买家演示账号。
- 首页与列表均有加载、错误提示；列表支持刷新和空状态。

模拟付款不连接支付渠道、不产生真实扣款。当前前端会话和 localStorage 可被用户修改，模拟校验不构成生产安全边界，也不保证跨浏览器标签页的事务一致性。接入真实后端时可将这两个方法替换为 `GET /api/orders` 和 `POST /api/orders/:id/mock-pay`；服务端必须独立鉴权、按用户筛选订单，并在事务中完成状态校验、更新、支付流水和日志写入。

## 申请退款

买家在“我的订单”点击“申请退款”，填写退款类型（仅退款 / 退货退款）、原因和金额，可选上传凭证。待发货订单仅支持“仅退款”；未付款、已有进行中售后或已退款订单不能重复申请。

`orderApi.applyRefund(orderId, payload)` 校验当前买家归属、订单状态、退款类型、原因和金额（大于零、不超过订单金额、最多两位小数），创建 `after_sale_tickets` 工单并写入售后状态日志。`after_sale_status` 更新为 `APPLIED`，页面显示“退款审核中”，原订单履约状态保持不变。提交成功自动返回订单列表，可展开工单查看金额、原因和凭证；刷新后仍保留。

凭证为选填，最多 3 张 PNG/JPEG/WebP，每张不超过 300 KB，通过 FileReader 转为 data URL 存入模拟工单 `evidence_urls`。本地存储空间不足时会提示失败，不会仅更新订单状态。此功能不上传服务器、不执行真实退款，也未实现商家审核操作。生产环境需改为受控文件上传，并由后端校验文件、保存凭证地址及处理审核退款。

运行回归测试：

```bash
node --test tests/orders.test.cjs
```

## 数据库

执行 `database/schema.sql` 可创建数据库与核心表。`orders.order_status`（订单状态）和 `orders.after_sale_status`（售后状态）是两个独立字段，业务上互不覆盖。
