# 商城管理系统

一个零依赖、可直接在浏览器运行的电商后台原型，包含：

- 普通买家公开注册，以及普通买家、商家、管理员三种身份的登录
- 根据角色自动进入不同后台
- 买家登录后进入购物平台首页，可查看历史订单、体验模拟支付
- 用户、商品、订单、订单明细的 MySQL 8 数据库设计
- 购物车、收货地址、支付流水、售后工单和状态变更日志
- 订单状态与售后状态独立建模

## 导航与功能规划

后台侧栏点击后切换实际内容并高亮当前栏目。管理员用户管理、商家审核、商品治理，以及商家商品管理、订单管理、售后管理、店铺设置均已接入可操作的本地模拟接口。买家中心的收货地址、个人资料及商城专题分类仍为规划占位页。

商城顶部栏目、五个商品分类和“探索秋日新选”入口也支持页面切换；占位页面可返回首页。首页新增“买家中心”入口。占位功能明确标注尚未实现，不执行模拟保存或伪造操作成功。

## 运行

直接双击 `index.html`，或在本目录启动任意静态文件服务器：

```bash
python -m http.server 8080
```

然后访问 `http://localhost:8080`。

## 商家商品列表

使用 `merchant@demo.com / 123456` 登录，“商品管理”可查看本店商品，新增或编辑名称、描述、售价、库存及上架状态；商品目录持久化并与商城首页共用。平台限制上架的商品不能被商家自行重新上架，新增商家只能管理本店商品。结算会校验在售状态、店铺营业状态和库存，并扣减库存。

## 商品治理、售后及店铺设置

- 管理员“商品治理”：查看全部商品、填写原因后下架并限制上架、解除限制、查看操作记录。解除限制不自动上架，需商家重新上架。下架会阻止新加入购物车及结算，已创建订单不受此商品状态变更影响。
- 商家“售后管理”：按本店筛选工单，查看原因、金额、凭证；同意或拒绝申请（拒绝必须填写原因），同意后执行模拟退款。退货退款的最终按钮表示商家已确认收到退货，未连接真实物流。保存商家回复、售后日志和模拟退款记录，并同步买家订单售后状态；原履约状态不覆盖。退款不自动补库存，避免未收货商品直接重新售卖。
- 商家“店铺设置”：保存店铺名称、联系方式、介绍、配送说明、售后说明和营业状态。暂停营业后本店商品不再展示，已有购物车不能新结算，历史订单仍可处理。
- 商家“订单管理”：显示本店订单，可对已付款且无进行中售后的订单执行模拟发货。

这些操作均在原模拟数据库中持久化，未连接真实支付、物流或 MySQL。页面统计概览仍明确标注演示数据。

## 管理员操作

### 平台售后介入

管理员侧栏“售后介入”展示全平台售后工单、买卖双方 ID、申请金额、原因和凭证。填写处理原因后，可点击“强制退款（模拟）”或“驳回申请”，在二次确认区域核对订单、金额和原因再提交。`orderApi.listPlatformTickets()` 与 `orderApi.interveneRefund(ticketId, decision, reason)` 均校验管理员权限。

强制退款按工单申请金额处理，可覆盖商家已拒绝的最新申请；不允许处理已退款、已关闭、已有新申请或已被平台裁决的工单。平台驳回不会产生退款记录。处理后同步买家及商家售后状态，保存管理员 ID、时间、原因、状态日志和模拟退款记录；全额退款同步支付流水状态，原履约状态不变。所有变更同一次写入本地模拟数据库，不执行真实扣款或退款。

使用 `admin@demo.com / 123456` 登录，进入“用户管理”查看所有账号的姓名、邮箱、角色、状态，可封禁/解封普通买家和已开通商家。管理员账号受保护，待审核账号不能通过解封绕过审核。封禁会阻止登录、刷新恢复会话及后续订单/购物车/退款接口操作；其他同源标签页也会响应账号状态变更。

“商家审核”预置 `apply1@demo.com`、`apply2@demo.com` 两条申请（密码均为 `123456`），展示店铺、联系人、说明、申请时间和审核状态。点击通过后开通商家登录；拒绝必须填写原因，拒绝后不可登录。审核结果、备注、操作人和时间保存在账号的 `merchant_application` 字段中。重复审核被拦截；现有 `merchant@demo.com` 保持已开通状态。

账号状态与审核结果使用 `ecom_users` 持久化，不清除现有注册账号。账号列表接口不返回密码；管理员权限从当前存储账号读取，不信任会话里的角色字段。当前仍是前端模拟权限，不能替代真实后端鉴权。本次未增加公开入驻申请提交页或管理员手动创建账号页面。

## 订单与模拟接口

登录买家账号后，点击右上角“我的订单”查看当前账号的历史订单。首页与订单列表均可执行模拟支付；支付成功后订单由“待付款”变为“待发货”，刷新或重新登录后状态仍保留。商家和管理员的订单表读取同一份数据。新注册买家没有历史订单，不会继承演示账号的订单。

- `mock-api.js` 提供异步的 `orderApi.listOrders()` 和 `orderApi.payOrder(orderId)`，从当前会话确定身份，不接受调用方传入买家 ID。
- 模拟数据存储在 localStorage 的 `ecom_order_db_v1` 中，包含订单、商品明细、售后工单、支付流水和状态日志。售后状态独立展示，付款不会覆盖售后状态。
- 字段、状态枚举与 `database/schema.sql` 对齐：`PENDING_PAYMENT` 显示“待付款”，`PAID` 显示“待发货”。未连接 MySQL，演示种子数据不是实际交易数据。
- 支付仅允许买家操作自己的待付款订单；重复支付已付款订单不会重复生成流水。旧版 `demo_order` 的已支付记录在首次初始化时迁移到固定买家演示账号。
- 首页与列表均有加载、错误提示；列表支持刷新和空状态。

模拟付款不连接支付渠道、不产生真实扣款。当前前端会话和 localStorage 可被用户修改，模拟校验不构成生产安全边界，也不保证跨浏览器标签页的事务一致性。接入真实后端时可将这两个方法替换为 `GET /api/orders` 和 `POST /api/orders/:id/mock-pay`；服务端必须独立鉴权、按用户筛选订单，并在事务中完成状态校验、更新、支付流水和日志写入。

## 购物车

每张商品卡片支持“加入购物车”，右上角“购物车”进入列表。同一商品重复加入会累加数量，支持加减（1–99 件）、移除、单选和全选，合计仅计算勾选商品。购物车按买家账号隔离，刷新后仍保留。

结算按模拟商品目录的价格生成 `PENDING_PAYMENT` 订单及商品明细（按商家分单），只移除已结算商品，未勾选商品保留。订单与购物车在同一次本地存储写入中保存，失败时不清空购物车；成功后进入“我的订单”，可继续模拟支付和申请退款。演示未收集收货地址，不连接真实库存、物流或支付服务。

模拟接口：`getCart()`、`addToCart(productId)`、`updateCart(productId, patch)`、`selectCart(selected)`、`removeFromCart(productId)`、`checkoutCart()`。现有订单和退款数据保持不变，购物车保存在同一模拟数据库的 `carts` 字段中。

## 申请退款

买家在“我的订单”点击“申请退款”，填写退款类型（仅退款 / 退货退款）、原因和金额，可选上传凭证。待发货订单仅支持“仅退款”；未付款、已有进行中售后或已退款订单不能重复申请。

`orderApi.applyRefund(orderId, payload)` 校验当前买家归属、订单状态、退款类型、原因和金额（大于零、不超过订单金额、最多两位小数），创建 `after_sale_tickets` 工单并写入售后状态日志。`after_sale_status` 更新为 `APPLIED`，页面显示“退款审核中”，原订单履约状态保持不变。提交成功自动返回订单列表，可展开工单查看金额、原因和凭证；刷新后仍保留。

凭证为选填，最多 3 张 PNG/JPEG/WebP，每张不超过 300 KB，通过 FileReader 转为 data URL 存入模拟工单 `evidence_urls`。本地存储空间不足时会提示失败，不会仅更新订单状态。此功能不上传服务器、不执行真实退款；商家可在“售后管理”处理申请。生产环境需改为受控文件上传，并由后端校验文件、保存凭证地址及处理审核退款。

## 数据库

执行 `database/schema.sql` 可创建数据库与核心表。`orders.order_status`（订单状态）和 `orders.after_sale_status`（售后状态）是两个独立字段，业务上互不覆盖。
